# Testuvalka

Асинхронний рушій математичного тестування для дистанційного навчання. Видає
числовий бал і знижує вигоду від списування (насамперед з чат-ботів) без
проктóрингу й без верифікації особи. Повний опис задачі й ухвалених рішень — у
`BRIEF.txt`.

## Як це протидіє списуванню (коротко)

Захист не в «детекції», а в побудові шкали (розділ 3 брифу) — усе реалізовано:

- **Пропускна здатність.** Багато коротких пунктів, на кожен жорсткий серверний
  таймер, бал = частка правильних. Цикл «скрін → бот → ввід» краде час і топить
  бал сам собою.
- **Індивідуальні числа** через HMAC(secret, прізвище+група+тест+…): обмін
  відповідями в чаті групи марний.
- **Обрив → перевидання** тієї самої задачі з іншими числами й повним часом;
  **пізня відповідь не оцінюється**, навіть правильна.
- **Проміжні поля** з перенесенням помилки (carry): копіювати треба весь ланцюг.

Стеля чесна: бот ≈50–70%, хто володіє темою ≈85–100%. Нуля списування не буде.

## Структура

```
engine.py            математичне ядро: генерація задач, перевірка, seed
app/
  config.py          секрет, БД, токен викладача, таймаут (усе з оточення)
  db.py, models.py   SQLAlchemy; еталони в БД НЕ зберігаються — усе з seed
  service.py         цикл: старт / поточне питання / відповідь / логіка часу
  grading.py         оцінювання в підпроцесі з таймаутом (реєструє банк і там)
  bank/              БАНК ШАБЛОНІВ по темах (сюди додаються задачі)
  load_tests.py      завантажувач тестів із YAML
  teacher.py         журнал оцінок (CSV) і сигнали аномалій
  main.py            FastAPI: API + статика
web/
  index.html         сторінка студента (KaTeX, таймер від сервера, телеметрія)
  teacher.html       кабінет викладача (журнал, аномалії)
tests/               pytest: цикл, час, вхід, завантажувач, кабінет, фронтенд
tests.yaml           опис тестів
```

## Запуск (розробка)

```bash
pip install -r requirements.txt
cp .env.example .env        # задайте TESTUVALKA_SECRET і TESTUVALKA_TEACHER_TOKEN

pytest                      # усі перевірки

python -m app.load_tests tests.yaml       # завантажити тести в БД
uvicorn app.main:app --reload             # сервер на http://127.0.0.1:8000
```

- Студент: `http://<host>/?test=<ключ>` → вводить прізвище+ім'я і групу.
- Викладач: `http://<host>/teacher.html` → ключ тесту + токен викладача.

## Як завести тест (YAML)

Тести описуються в `tests.yaml` і завантажуються `python -m app.load_tests
tests.yaml` (повторний запуск оновлює за ключем). Приклад:

```yaml
- key: derivatives_1
  title: Похідні (1 курс)
  question_count: 12          # не більший за розмір bank (ключі не повторюються)
  points_per_question: 0.5    # кожне питання важить 0.5 -> усього 12*0.5 = 6
  bank: [derivative_at_point, chain_rule, product_rule, ...]
  opens_at: 2026-09-20T08:00  # необов'язково (UTC); без цього тест відкритий завжди
  closes_at: 2026-09-22T20:00
  max_attempts: 2
  max_reissues: 2
```

`points_per_question` (необов'язкове) задає вагу кожного питання незалежно від
кількості полів усередині; часткові бали нормуються до неї. Без нього підсумок =
сума «сирих» балів полів. `bank` може бути більшим за `question_count` — тоді
кожен студент отримує випадкову підмножину (більше варіантів).

## Як додати шаблон задачі (Python)

Шаблони — це параметричні генератори з валідацією; лишаються кодом. Кладіть їх у
`app/bank/<тема>.py` і додавайте рядок `import` у `app/bank/__init__.py`.
Зразок — `app/bank/algebra_lines.py`; докладніше про формат — `BRIEF.txt` (розд. 4)
і три приклади в `engine.py`.

Прийом, що економить час: спершу задайте ВІДПОВІДЬ цілими числами, потім із неї
виведіть умову (красиві числа без перебору). Обов'язково додайте цикл валідації
параметрів (уникати ділення на нуль, некрасивих коренів тощо).

**Конвенція запису умов і підписів (для KaTeX):** проза — звичайним текстом,
математику загортайте в `$...$` (інлайн) або `$$...$$` (блок), переноси рядків —
`\n`. Приклад: `"Розв'яжіть рівняння: $x^2 - 5x + 6 = 0$"`.

**Форми відповіді.** Перевірка алгебраїчна (через sympy), тож різні записи одного
числа рівнозначні: `5/2`, `10/4`, `2.5` і `2,5` (десяткова кома) — усе зараховано.
Тому тримайте еталон у найзручнішій формі; студент може відповісти будь-якою.

## Кабінет викладача

- `GET /api/teacher/results?test_key=…` → CSV-журнал (UTF-8 з BOM, відкривається
  в Excel). Стовпці: група, прізвище, № спроби, статус, бал, %, час.
- `GET /api/teacher/anomalies?test_key=…` → сирі сигнали (вставки, перемикання
  вкладки, час на пункт). Це **не звинувачення**: пороги для автоматичного
  скасування спроби (п. 3.4/6.4) підбираються за даними пілоту й свідомо тут не
  автоматизовані.
- Доступ — за токеном: заголовок `X-Teacher-Token` або `?token=` (для прямого
  посилання на CSV). Без `TESTUVALKA_TEACHER_TOKEN` кабінет вимкнено (503).
- Зручніше — сторінка `web/teacher.html`.

## Розгортання (безкоштовно)

Застосунок — це звичайний контейнер (Dockerfile у корені). Йому потрібне
середовище, що виконує **справжній процес** (safe_grade створює підпроцес), тож
serverless/edge (Vercel, Cloudflare Workers) НЕ підходять. Актуальні (2026)
безкоштовні варіанти під наш профіль:

**A. Найнадійніший (без сну): Oracle Cloud Always Free, ARM-ВМ, Франкфурт.**
4 OCPU / 24 ГБ / 200 ГБ — з запасом; ВМ **не засинає** (немає холодного старту).
Ставите Docker, запускаєте контейнер, БД — SQLite на постійному диску (для 25
студентів досить) або Postgres-контейнер; HTTPS через Caddy. Мінус: разове
налаштування ВМ (~1-2 год) і картка для реєстрації (Always Free не списує).

**B. Найпростіший (з холодним стартом): Render (Docker) + Neon (Postgres).**
Блупринт — `render.yaml` (регіон Франкфурт, план free). Мінуси: free-сервіс
Render засинає після ~15 хв (прокидання 30-60 с), а його CPU слабкий (0.1). Тому:
БД — окремо в **Neon** (free, ЄС), а перед вікном тесту «будіть» сервіс зовнішнім
пінгером (cron-job.org / UptimeRobot). Безкоштовний Postgres самого Render живе
лише ~30 днів — не використовувати. Аналог Render — **Koyeb** free (Франкфурт,
засинає за 1 год, без картки).

**Чесно:** холодний старт — головний ворог (розд. 6.7 брифу). Якщо можлива
символічна плата — **Hetzner CX22 (~4 €/міс)** знімає весь цей клас проблем. Fly.io
у 2026 вже не має безкоштовного тиру (~2 $/міс).

Обов'язкові змінні оточення: `TESTUVALKA_SECRET` (сталий!), `TESTUVALKA_TEACHER_TOKEN`,
`TESTUVALKA_DATABASE_URL` (Postgres у проді або `sqlite:///…` на постійному диску),
`TESTUVALKA_AUTOLOAD=tests.yaml`. `TESTUVALKA_SECRET` у git не комітити.

**SQLite на ефемерній ФС стирається при передеплої** — у проді лише Postgres або
постійний том.

### Як доповнювати тести після розгортання

Завдяки `TESTUVALKA_AUTOLOAD=tests.yaml` тести перечитуються з файлу **на кожному
старті** (upsert за ключем):

- **PaaS (Render/Koyeb):** відредагуйте `tests.yaml` (і, для нового шаблону, файл
  у `app/bank/`) → `git push` → авто-редеплой → тести оновлено. Шелу не треба.
- **ВМ (Oracle/Hetzner):** `git pull` і перезапуск контейнера
  (`docker compose up -d --build`), або разово `python -m app.load_tests tests.yaml`.

Новий ШАБЛОН задачі — це код, тож у будь-якому разі потребує редеплою; новий
ТЕСТ на наявних шаблонах — лише рядок у `tests.yaml`. Наявні спроби студентів
завантажувач не чіпає.

### Вивантаження оцінок

Так, вивантаження результатів є (кабінет викладача, розділ вище): відкрийте
`/teacher.html`, введіть ключ тесту й `TESTUVALKA_TEACHER_TOKEN` — побачите журнал
і кнопку **CSV** (UTF-8 з BOM, відкривається в Excel), а також сигнали аномалій.
Пряме посилання: `GET /api/teacher/results?test_key=…&token=…`.

## Відомі місця для рефакторингу

- `app/grading.py` створює пул процесів на кожен запит (п. 5.8) — тому таймаут
  великий (15 с, включає холодний імпорт sympy). У проді — один довгоживучий
  теплий пул, тоді таймаут падає до ~3 с. На Linux (fork) холодний імпорт не
  повторюється, тож там уже помітно швидше.
- `question_count` тесту обмежений розміром банку: seed задачі не залежить від
  порядкового номера, тож повтор ключа в межах спроби дав би тотожні числа.

## Windows: spawn і оцінювання

На Windows підпроцеси створюються через `spawn` (дочірній заново імпортує
модуль воркера). `uvicorn` і `pytest` мають потрібний захист самі. Якщо пишете
власний разовий скрипт, що прямо чи опосередковано кличе оцінювання, ховайте код
під `if __name__ == "__main__":`, інакше дочірній процес рекурсивно спробує
запуститись знову. На Linux (fork) цього нюансу немає.
